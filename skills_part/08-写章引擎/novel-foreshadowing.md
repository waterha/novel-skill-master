# novel-foreshadowing - 伏笔追踪与回收

## 目标

让每个伏笔都有来源、目的、上下文和回收窗口。写作时只处理当前真正需要的伏笔，不为了“记得伏笔”而机械回收。

## 唯一账本

使用 `.story-system/foreshadowing.json`。字段以 `references/guides/novel-project-schema.md` 的“伏笔账本”章节为准。知识图谱中的伏笔节点只作检索索引，不能替代账本。

初始化和检查：

```text
python tools/foreshadowing_tracker.py init --project-root <项目根>
python tools/foreshadowing_tracker.py validate --project-root <项目根>
```

## 写前检查

每次写章前运行：

```text
python tools/foreshadowing_tracker.py due --project-root <项目根> --part P --volume V --chapter N
```

按结果处理：

- `not_due`：本章不处理，避免过早提醒。
- `available`：允许自然强化或回收，但必须服务本章事件，不能强塞。
- `due_soon`：检查未来 3 章章纲，安排强化或回收位置。
- `due`：本章任务卡必须写明“回收、部分回收或延期”及原因。
- `overdue`：阻断正常写作；先提出回收方案，或取得用户确认后记录延期窗口和代价。
- `conditional`：读取触发条件和当前状态，明确本章是否已经触发。

需要处理某条伏笔时，读取它的 `purpose`、原文 `evidence`、读者初读印象、计划真相、前后章节摘要、强化记录和回收窗口；再根据账本中的正文路径完整读取埋设章及前后各 2 章，确认当时场景语气、人物知识和读者已知信息后决定回收方式。

## 回收设计

先回答四个问题：

1. 回收解决什么当前问题，而不只是解释过去？
2. 哪个角色通过什么行动发现或触发它？
3. 回收后读者对旧场景产生什么新理解？
4. 回收造成什么人物、关系、资源或目标变化？

可选择直接揭示、行动兑现、物件再现、对话反转、身份重释、局部答案引出更大问题等方式。长伏笔优先让回收参与高潮因果，不用一句解释完成。

若延期，更新 `payoff` 窗口、延期原因、下次强化位置和用户确认记录。延期不是忽略。

## 写后检测与登记

正文完成后运行候选检测：

```text
python tools/foreshadowing_tracker.py detect --chapter-file <正文路径>
```

逐条结合章纲和语义判断：

- 新信息是否故意为未来事件提供条件、疑问或双重解释。
- 旧伏笔是否被重复提醒、改变意义或提高重要性。
- 本章是否真正完成回收，还是只给出部分答案。

候选词只能帮助定位，不能自动认定伏笔。确认后使用临时 JSON payload 调用 `upsert`，记录：伏笔 ID、标题、为何留下、埋设位置、原文证据、读者印象、计划真相、回收窗口、预计方式、状态和历史。写入成功后删除临时 payload；正式记忆只保留统一账本。

新埋设伏笔必须在本章完成报告前进入账本。已回收伏笔必须记录实际回收章节、方式、证据和造成的变化。

## 前后章节上下文

每章写后运行：

```text
python tools/foreshadowing_tracker.py refresh-context --project-root <项目根> --chapter N --window 2
```

工具将伏笔埋设章前后各 2 章的内容摘要、正文路径和缺失情况写入该伏笔的 `context.nearby_chapters`。未来章节尚未写时先记录已有部分；后两章完成后自动补齐。若摘要缺失，先回读正文并补写章节事实摘要，再宣告伏笔上下文完整。账本保存摘要和路径，不重复复制整章正文。

## 完成标准

- 账本 JSON 校验通过。
- 本章到期和逾期伏笔均有明确决定。
- 本章新增、强化、部分回收和完全回收均已登记。
- 埋设章附近上下文已刷新，缺失摘要有明确待办。
